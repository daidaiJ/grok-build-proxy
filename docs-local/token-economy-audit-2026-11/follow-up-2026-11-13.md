> 默认模型 `relay/deepseek-flash`（1M 窗口）。数据源：
> `~/.grok/cache/model-usage.jsonl`（11-03 → 11-13，1910 次主回合请求）、当前与
> 历史会话工件（`tool_definitions.json` / `chat_history.jsonl` / `prompt_context.json`）、
> relay 只读探针。前篇见 [`README.md`](README.md)。

## 0. 结论

1. **稳态命中已到实际天花板**：98.3% 的 prompt token 命中，日粒度 98.2–99.1%。
   剩余未命中 4.65M / 10 天里，13% 是首轮冷启动，其余是每轮新增内容
   （工具输出 + 上一轮回复），属不可压部分。
2. **工具 schema 的会话路径已修完**：v1.0.74 活体确认 `send_feedback` 描述跨会话
   逐字节一致；本会话首轮仍只命中 12,288（服务端缓存还是旧前缀，断点在旧
   `send_feedback` 描述内部），**下一次新会话应升到约 16k**（system 3.5k +
   tools 12.5k）。`spawn_subagent` 的模型清单是 schema 里**唯一剩下的动态字节**。
3. **钱的大头已经不是缓存未命中**：输出 1.36M（其中 reasoning 0.815M，60%）与
   未命中 4.65M 各占约三分之一。**会话基座实测约 56k tokens/轮**（旧审计按
   bytes/4 估成 40k，低估了中文规则），其中 `Agents.md` 规则约 27–34k（`grok inspect` 估 27.4k，按字符面估 34.5k）。

## 3. 仍影响缓存稳定的面（按爆炸半径排序）

### 3.1 `spawn_subagent` 的模型清单（唯一剩余动态 schema 字节）

- 位置：工具序 **#9**，累计约 3.5k tokens 处开始；清单由
  `TaskModelPresentation.model_slugs` 渲染（`agent/builder.rs:948`、
  `remote_config/task_model_policy.rs:110`），排序去重后写进描述。
- 实测变化：11-11 会话是 9 个 slug（`cc-*` / `cline-*` / `step-*`），11-12 起
  变成 7 个（`relay/*` 系）——配置改一次，schema 字节变一次。
- 爆炸半径：断点在 #9，其后 28.7k chars（约 9k tokens）的工具说明 + 首条 user
  消息（规则 34.5k + skills 5.2k + MCP 1k）**全部作废**，单次约 50k tokens 转
  uncached。
- 触发面：每个新会话在 spawn 时按当时 catalog 解析一次；会话内
  `x.ai/internal/reload_models` 只换 models manager，不重建会话 agent
  （`extensions/session_admin.rs:729`），所以**会话内不会闪断**，跨会话每次
  配置变更断一次。
- 低成本修法（未施工）：把清单从 schema 移到首轮 system-reminder（追加块）或
  工具错误回包（沿用 `send_feedback` 模式）；schema 保持与配置无关。

### 3.2 只有主模型带两个缓存能力位

`~/.grok/config.toml` 里只有 `relay/deepseek-flash` 配了
`prune_mode = "append"` + `system_prompt_update = "in_history"`。切到
`relay/glm-5.3-flash`、`relay/gpt-6-luna`、`ocgo-deepseek-v4.1-flash`
（1M 窗口）任一条目，就会回到「50% 线原地改写 + 头部就地换字节」的旧行为
（`request_builder.rs:131`、`types.rs:1357` 默认 Rewrite）。`lightvela/auto`
只有 200k 窗口，append 模式不释放 token，建议保持 rewrite 或换大窗口模型。

### 3.3 图像预算原地驱逐

`image_budget.rs:147` 在请求体超过预算时**原地**从历史里驱逐旧图，被驱逐点
之后的前缀整段作废。纯文本会话不触发；贴图多的长会话是唯一风险面。

### 3.4 已确认安全、无需再动的面

- 会话内工具数组：MCP 工具不进顶层数组（`prepare_tool_definitions_inner`
  走 `tool_definitions_builtins_only`，`sampler_turn.rs:516`，MCP 经
  `use_tool`/`search_tool` 暴露）；plan 模式过滤是 no-op
  （`session_mode.rs:23-28`）；MCP 晚连接/失败不改变数组。
- 日期跨天：`reminders.rs:509` 以追加 system-reminder 表达，不改写头部。
- 工具结果裁剪：`prune_mode=append` 只在被裁结果后插失效标记
  （`request_builder.rs:287`），保留原字节；`mutations.rs:338` 在 append 下
  直接跳过保留会话的原地硬清。
- resume：顶层会话冷载保留 journal 旧 head，不重写首条 user 消息。
- reasoning 回传：`conversation_to_chat_messages` 把 Reasoning 折进
  `reasoning_content`（`chat_completions.rs:192-213`）。relay 只读探针：
  给 assistant 消息加 1500 词 `reasoning_content`，`prompt_tokens` 51 → 51
  （与不加完全相同），**该端点不计入、不影响前缀**，无需剥离。

## 4. token 体量拆解

首轮请求实测 55,375 tokens，按同批字节反推（中文约 1 token/字、ASCII 约
3.2 字符/token）：

| 组成 | 字符 | 约 token | 占比 |
|---|---|---|---|
| system prompt | 11,173 | 3.5k | 6% |
| tool definitions（23 个） | 40,009 | 12.5k | 23% |
| 首条 user：`<user_info>` + 规则（Agents.md 70.5k chars） | 75,764 | 27–34k | 60%± |
| skills 目录 reminder | 16,706 | 5.2k | 9% |
| MCP 服务器 reminder | 3,199 | 1.0k | 2% |

基座每轮都在（cached 计价约 $0.20/10 天，但在上下文中占 38% 的平均占用）。
两个可观测量：

- **规则 doc 是单一最大块**：`Agents.md` 约 34.5k tokens/轮，历史 TODO 与
  Handoff 占大头；归档后可直接减半（纯内容改动，零代码风险）。
- **skills 目录随插件增减**：11-12 会话 78 项 / 23.2k chars，11-13 会话 50 项 /
  16.7k chars（少了 28 个 lark 技能）。它排在规则之后，变化只丢尾段，不污染
  工具前缀。

其他体量面：

- 工具输出上限：bash 本机 40k chars（`[toolset.bash] output_byte_limit`，
  缺省 200k，`agent/config.rs:1205`），截断保留头尾 + 全量文件路径；
  MCP 输出默认 20k bytes（`util/mcp_truncate.rs:32`）；grep 有行预算。
  `[tool_output_compression]` 默认关（一期有损，不建议开）。
- **turn_summary sidecar**：默认开，每个完成回合一次独立调用（fresh conv id，
  system + ≤4k 用户文本 + ≤32k 回复文本，`turn_summary.rs:60-130`）。它走
  `conversation_collect` 而不是主回合循环，**不写 `/stats` 账本**
  （账本只在 `turn.rs:3489` 追加），所以现有数据无法量化——账本里没有任何
  低于 22k prompt 的行即可佐证。
- 主回合没有额外隐藏调用：recap / compaction / btw 都走 `side_call` 的
  缓存对齐请求；title 生成已关。

### 5.1 施工状态（2026-11-13）

P0 配置已应用：`relay/glm-5.3-flash`、`relay/gpt-6-luna`、
`ocgo-deepseek-v4.1-flash` 补上 `prune_mode = "append"` +
`system_prompt_update = "in_history"`；`lightvela/auto`（200k 窗口）保持默认。
备份 `~/.grok/config.toml.bak-token-econ-20261113-100330`。

同日按 35 天账本（134 会话 / 10,449 主回合）与**实际账单费率**（input $0.15 / cache read $0.03，即 1/5，不是 catalog 的 1/50）重估：近期 10 天真实成本约 $9.6（cached 占 85%），因此 cached 体积是主项。结论：关闭中途裁剪，并把窗口从 500k 下调到 300k（80% = 240k 压缩）。按控制集模拟，300k/80 相对 1M 省约 39%，中位 TTFT 3.9→3.5s、p90 7.1→4.6s，压缩约 4.3 次/10 天；500k 只省约 22%。裁剪无论 append/rewrite 都更贵（300k 下 +$0.2/+$0.5 每 10 天）。

同时修正一个从 11-12 起就存在的配置错误：`system_prompt_update` 的合法枚举值是
`in_history`（serde snake_case），此前写的 `"in-history"` 被配置解析拒绝
（`grok inspect` 报 `unknown variant`），**该能力位实际一直是 `off`**。改成
`in_history` 后 `grok inspect` 只剩既有的 `[consent] unrecognized` 一条告警。
本机配置摘要与变更说明另见 `D:\pro\agent-teams-docs\grok-token-economy-config-changes.md`。
