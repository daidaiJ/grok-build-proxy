# 统一池周用量跳变排查记录（2026-W39：7%→76%）

> **状态（2026-09-27）：本机侧排查完成，他机对账未做。** 结论：本机排除，消耗来自
> 账号其他统一池面；首嫌疑 = 另一台设备上的 xAI 直连 agentic 会话。跨设备对账
> playbook 见 §5。配套工具 `scripts-local/quota_audit.py`（只读本地文件，零网络请求）。
> 关联：[`usage-quota-estimate-todo.md`](usage-quota-estimate-todo.md)（额度反推功能设计，

## 1. 现象

SuperGrok 周池（`isUnifiedBillingUser=true`，周期 09-22 23:50 → 09-29 23:50 UTC）
在相邻两次计费采样之间从 7% 跳到 76%（+69 点），而窗口内本机零活动。用户自述
24/25 号上班都在用第三方模型，疑惑消耗来源。

## 2. 排查链路（本机四步，可复现）

### 步骤 1：pct 轨迹提取（unified.jsonl 的 billing 采样）

shell 每次成功拉取计费配置写一条 `billing: fetched credits config`（96 条）。
提取 `ctx.config.creditUsagePercent` + `currentPeriod`：

| 北京时间 | pct | 说明 |
| --- | --- | --- |
| 09-22 23:48 | 26% | 旧周期（09-15 起）尾读数 |
| 09-23 07:50 | — | **新周期开始** |
| 09-23 20:31 → 09-24 23:05 | 1% → 7% | 日常爬升 ≈4–6 点/天 |
| **09-24 23:05 → 09-25 19:14** | **7% → 76%** | **+69 点，中间无采样点** |
| 09-25 19:20 → 09-26 17:59 | 77% → 78% | 回到日常爬速 |

注：pct 全部为整数量化（1/2/5/6/7/26/76/77/78），采样只在本机 CLI 拉计费时产生
（≈每次 turn 结束），所以"跳变窗口"的上界精度受采样密度限制。

### 步骤 2：本机账本聚合（cache/model-usage.jsonl）

1488 条调用（09-22 22:42 起），按模型聚合：**全部**是第三方网关模型
（deepseek-v4.1-flash / deepseek-v4-flash / glm-5.3-flash / xiaomi/mimo，分别走
Command Code 与火山 Ark），**xAI 直连调用为 0**，本周如此、全程如此。
第三方流量不过 xAI，对统一池贡献 = 0。

### 步骤 3：跳变窗口活动核查（三重证据）

窗口 = 北京 09-24 23:05 → 09-25 19:14：

| 证据源 | 结果 |
| --- | --- |
| model-usage.jsonl（窗口过滤） | **0 次模型调用** |
| unified.jsonl 按小时分布 | 北京 01:00–19:00 **0 条**（22:00–23:59 有 ~1800 条 = 24 日晚重度会话；00:00–00:59 仅 3 条收尾；19:00 起恢复） |
| sessions/ 文件 mtime | 窗口内 **0 个文件变动** |

### 步骤 4：config 审计（有没有会摸到 xAI 的隐藏面）

- 6 个 `[model.*]` 全部带第三方 `base_url`（api.commandcode.ai / 火山 Ark /
  token-unlimited.com / 小米），无一指向 xAI；
- 唯一默认后端（= api.x.ai）配置：`[ui] fork_secondary_model = "grok-4.6"`
  （会话 fork 时的辅助模型）——全量日志中 **grok-4.6 零调用痕迹**（6076 条
  "grok-pager" 命中是客户端标识非模型 id）；
- 无 memory/embedding/compaction/title 指向 xAI 的配置。

**结论：本机三层（账本/日志/会话）+ 配置面全部排除。69 点消耗来自账号的其他
统一池面。**

## 3. 量级推断（缩小嫌疑面）

- 日常背景燃烧：09-23/24 两天 ≈4–6 点/天，且本机同期贡献为 0 → 网页/App 有日常
  轻度使用（或另一设备低强度使用）；
- 跳变：+69 点 / ≤19.2h ≈ **日常速率的 15–20 倍** → 主燃烧器是一次"重事件"
  （重会话/批量生成/长任务的集中爆发），不是日常背景燃烧的累积。

## 4. 什么会触发统一池消耗（候选面，按嫌疑排序）

| # | 候选面 | 触发条件与特征 | 怎么核对 |
| --- | --- | --- | --- |
| 1 | **另一台设备的 agentic 编码会话（xAI 直连）** | agent 每轮全量重发上下文，是单位时间燃烧最快的面；一次长上下文重会话（或并行 subagent）足以烧几十个点。上班日最自然。注意：只要有一个会话/一条 fallback 走了 xAI 直连（默认模型没改、fork 辅助模型、官方登录的别的 CLI）就会中招 | 那台设备跑 `quota_audit.py`，看跳变窗口内 xAI-direct tokens（§5.1） |
| 2 | **grok.com 网页 / 手机 App** | 统一池下与编码同桶；长对话 + Think/DeepSearch 单条消耗高；Imagine 生图/生视频按次且贵；语音长会话 | 不产生任何 CLI 日志（对账盲区），只能查 grok.com 用量页/App 内记录 |
| 3 | X(Twitter) 客户端里的 Grok | 是否计入统一池待确认 | grok.com 用量页看有无 X 侧明细 |
| 4 | 后台 agent（dashboard 派发）挂在别的设备 | 无人操作也会持续烧 | 同 #1，看那台设备的账本窗口 |
| 5 | 共享账号/凭据外泄 | 以上全对不上时的兜底嫌疑 | grok.com 账号设置的活跃设备/会话列表；必要时改密 |

**明确不占池**：第三方网关模型（Command Code / 火山 Ark / 小米 / token-unlimited，
流量不过 xAI）；本机 CLI（步骤 2/3 已排除）。

## 5. 他机对账 playbook

### 5.1 每台候选设备跑取证脚本

把 `scripts-local/quota_audit.py` 拷到目标设备（同账号的 Grok CLI 机器）：

```bash
python quota_audit.py                          # 全量轨迹 + 跳变检测 + 账本分模型
python quota_audit.py --window "2026-09-25 00:00,2026-09-25 19:14"   # 只看跳变窗口
```

输出解读：

- **billing samples / jump windows**：该设备自己的 pct 采样轨迹与窗口内本地活动；
- **token ledger 分模型表**：`XAI-DIRECT` 行是唯一动 pct 的流量（config 无
  base_url 或 api.x.ai 域名）。看窗口内 xAI-direct tokens 的**量级**；
- 第三方模型行与本案例的 deepseek/glm 一样，直接忽略。

**第一轮对账目标不是算精确点数，是找主燃烧器**：谁的窗口内 xAI 直连 token 量级
最大，谁就是 +69 点的来源。

### 5.2 对账公式

```
某设备贡献点数 ≈ 该设备窗口内 xAI-direct tokens ÷ Q × 100
Σ(各设备) + 网页/App/未记录面 = 69 点
```

Q = 周池 token 当量，服务端不下发（见关联文档），所以第一轮只比量级与排序。
缺口（Σ设备 < 69 点）= 网页/App/未记录面 → 走 §4 #2/#5 核对。

### 5.3 grok.com / App 侧核对

- grok.com 登录同账号 → 用量/Settings 页看有无分产品、分日明细；
- 手机 App 的用量通知/限流提示历史（"已用 X%"推送时间能当免费采样点用）。

### 5.4 09-30 07:50（北京）周期重置：两个免费实验

1. **干净起点**：重置后立刻（任何设备）跑一次脚本，确认 pct 归零、period start
   变为 09-29T23:50Z——之后的对账窗口全部切到新周期；
2. **单设备标定 Q**：新周期里只在一台设备跑一段已知 token 量的 xAI 直连会话
   （默认模型短会话即可），读 pct 增量 → `Q ≈ tokens ÷ Δpct × 100`。有了 Q，
   5.2 的公式就能出绝对点数，回填 09-25 案件。

### 5.5 若全部对不上

账单缺口找不到主燃烧器时：grok.com 账号设置查活跃登录会话/设备列表，确认
auth.json 凭据没有第二使用方，必要时改密重登。

## 6. 取证坑（本轮踩过的）

- **unified.jsonl 是活动文件**：本机排查期间窗口内条数在多次扫描间非单调变动
  （35/87/117），疑似并发滚动/重写。对账以**小时分布**与**账本（json 解析稳定）**
  为准，不要抠精确条数；另一设备上同理，扫完尽快落盘结果；
- pct 只在 CLI 拉计费时采样（≈每 turn 一次），跳变窗口的真实起点可能早于
  "前一个采样点"（采样密度决定精度）；
- pct 整点量化：Δpct=1 点内的 token 换算误差最高可达 ±Q/200；
- 账本只记成功推理：失败/中断的请求本地 0 token、服务端照算（系统性低估本机）。
