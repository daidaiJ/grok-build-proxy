## 2. 结构发现

1. **缓存命中已经不是问题。** 全窗口 98.6%；`cache-breaks.jsonl` 只有 3 条，全部是
   压缩造成的 `history_rewrite`，断崖后未命中合计 35k token ≈ `$0.0013`（0.04%）。
   #16 的检测只统计主回合，没有把 title/recap 的小前缀误报成断崖。
   继续投缓存优化的边际收益接近零。
2. **成本 ≈ 上下文大小 × 调用次数。** 78% 的钱花在“每轮重发并重读上下文”，
   调用次数与上下文水位是两个乘数。
3. **压缩水位直接决定平均上下文。** 当前 300K × 80% = 240k 触发，长会话平均 151k。
   用 786 次调用的真实增长序列回放（含压缩调用成本估算 `T×输入价 + 3k 输出`）：

   | 触发水位 | 成本 | 压缩次数 | 相对 240k |
   | --- | --- | --- | --- |
   | 140k | $1.078 | 11 | −25% |
   | 160k | $1.132 | 9 | −21% |
   | 180k | $1.188 | 7 | −17% |
   | 200k | $1.261 | 6 | −12% |
   | 220k | $1.371 | 5 | −5% |
   | 240k（现状） | $1.437 | 5 | — |
   | 300k | $1.677 | 4 | +17% |

   回放基线 `$1.437` 对实测 `$1.398` 偏高 3%，可作相对比较用。
   这张表只回答成本；质量维度（200–300k 注意力甜区）见 §3 P1。
   把窗口抬到 400K、触发 288–300k 后，全天回放里 200–300k 内的调用占比从 16.7%
   升到约 30%，成本 +8~9%（`$3.31`→`$3.60`），压缩 23→17–19 次。
4. **压缩本身没有记账。** `CallPurpose::Compaction` 枚举存在，但全仓没有记录点；
   `usage.json` 也只累加主回合。窗口内可辨认的压缩约 15 次（今天 3 次、两个晚高峰
   会话各约 6 次），每次约 `$0.01`，合计约 `$0.15`（约 5%）在账本和 `/stats` 中完全
   不可见；也无法回答“压缩花了多少、压缩后摘要多大”。
5. **输出是第二项。** 全窗口 18%（短会话 27–33%），其中 55% 是 reasoning；
   前 1% 的大输出调用占输出 token 的 12%（单次 13k 的规划/写文档回复）。
6. **固定前缀约 20k token/次。** 26 个工具、45,461 B（约 12–13k token），
   system prompt 11.9KB，AGENTS.md 8.5KB；首调用 17–23k token。
   工具面里 `workflow` 5.6KB、`reference_to_video` 5.0KB、`send_feedback` 4.1KB、
   `image_*` 3.3KB、`scheduler_*` 2.6KB、`lsp` 2.3KB，合计 27.3KB（60%），
   近 17 小时一次都没被调用。
7. **侧调用是小头但可修。** title/recap 类 5 次共 `$0.019`（0.6%）；短会话里
   title 可达 3.5%（2 次 title 合计约 218k 未命中——`tools=[]` 让前缀在工具边界
   处整段分叉）。`turn_summary` 今天 11/11 失败（`grok-4.5` + `cli-chat-proxy`，
   传输错误），不花钱，但每轮白试一次。

## 3. 下一步方案

### P0 压缩记账（先补可见性）

- 在 `crates/codegen/xai-grok-shell/src/session/compaction.rs` 的压缩采样返回后
  调用 `record_side_call_sample(CallPurpose::Compaction, …)`，单遍与 two-pass 两条
  路径都要覆盖；`/stats` 的 sidecar 视图纳入该用途。
- 验收：账本出现 `purpose=compaction` 行，`/stats` 能看到压缩的成本与次数；
  拿一次真实压缩核对行内 prompt/output 与压缩后基线的对应关系。
- 价值：不是省钱，而是让约 5% 的支出现在可测，否则压缩成本与压缩后基线都无法对账。

### P1 上下文窗口：300K/80% → 400K/72–75%（288–300k 触发）

- 推导：窗口只是容器，决定“活动上下文在哪”的是触发点。要同时满足
  “活动上下文 ≤ 300k（甜区上界）”和“不超窗”，需
  `窗口 ≥ 触发 + max_completion_tokens + 余量`；`300k + 65,536 = 365.5k`，
  所以窗口至少 ~366k，取 400k 留 34.5k 余量。
- 配置：`context_window = 400000`、`auto_compact_threshold_percent = 72`
  （288k，峰值留 12k 安全垫）或 `75`（300k，甜区上限）。`max_completion_tokens`
  保持 65,536；压缩输入 288–300k 仍在 verbatim 预算内（400k−32.7k−工具 13k≈354k）。
- 回放（全天 5 组、1,810 次调用）：

  | 配置 | 触发 | 压缩/天 | 全天成本 | 200–300k 内调用占比 | 峰值 |
  | --- | --- | --- | --- | --- | --- |
  | 300K/80%（现状） | 240k | 23 | $3.31 | 16.7% | 240k |
  | 400K/72% | 288k | 19 | $3.60 | 29.7% | 288k |
  | 400K/75% | 300k | 17 | $3.61 | 29.4% | 300k |
  | 400K/80% | 320k | 15 | $3.92 | 29.2%（7.2% 调用越过 300k） | 320k |

  `400K/80%` 会越过甜区上界，不作为候选。
- 无超窗风险：旧 1M 窗口下 `deepseek-flash` 有 254 次调用 prompt >300k、最大 398k
  （`model-usage.jsonl`），网关接受 398k 输入；新配置实际最多发 300k prompt +
  65.5k 输出预算 = 365.5k，落在已验证范围内。
- 代价：长会话 +17%（`$1.44`→`$1.68`），短会话因压缩次数减少基本持平；
  全天约 +9%。换来的是甜区时间接近翻倍、压缩次数减少 15–25%、超窗风险消失。
- 进一步把时间留在 200–300k 的杠杆是压缩后的基线（当前 17–66k），见 P2；
  基线越高，每个周期在 200k 以上的占比越大，同时均价也会上升。
- **已应用 2026-11-14 12:22**（备份 `~/.grok/config.toml.bak-token-econ-20261114-1222`）：
  `relay/deepseek-flash` 与 `relay/glm-5.3-flash` → `400000` / `72` / 输出 65,536；
  `relay/gpt-6-luna` → `256000` / `85` / 输出 32,768（217.6k + 32.8k = 250.4k < 256k）。
  glm 的 131,072 输出预算使 288k + 131k = 419k 超出 400k，因此同步降到 65,536；
  历史 glm 最大输出 30,537、p99 15,419，65,536 不会截断。当前会话仍在旧配置里，
  新会话生效。

### P1 输出/推理（质量换成本，需 A/B）

- reasoning 占输出 55%、占总成本 10–12%。实验：routine 回合用 `medium`
  （`/effort` 已有），plan/review 保持 `high`；或先把 subagent/explore 组降到 `medium`。
- 预期 4–8%；用返工率（重复读、重复改同一文件）作为质量闸门。

### P1 工具面收敛

- 把 `workflow`、`reference_to_video`、`image_*`、`send_feedback`、`scheduler_*`、
  `lsp` 改为延迟声明（需要把 `search_tool` 的目录从 MCP 扩到内建工具，或加
  配置级禁用列表）；目标 45.5KB → ~18KB。
- 预期 ≈4%（7.5k token × 1,865 次 × 缓存价）；顺带给 `search_tool` 加 schema 字节上限。
  不变动上下文窗口，也不减少历史信息。

### P1 行为：合并工具调用

- 单任务 786 次调用，每次都为整个前缀付费；调用数降 10% ≈ 成本降 7–8%。
- 先量 `calls/turn` 的分布，再试短提示（“独立读/搜合并到一轮”），A/B 看调用数与返工。
  这项直接减少“重读次数”，与上下文质量无关。

### P2 压缩后基线：先查清，不盲压

- 同样在 239k 触发，今天两个会话压缩后是 26.8k / 40.1k，昨晚长会话是 66–68k。
  候选原因：摘要长度、保留的最近轮次、two-pass prefire、会话级 compaction mode/detail。
- 在甜区假设下，66k 的基线比 26k 更接近最优区。只有确认多出来的是“摘要冗余”
  而不是任务细节时，才考虑压缩；否则保持或增大保留量。先做归因，不预设结论。

### P3 侧调用

- title refresh 只取最近 ~10k token（或保留 tools 前缀 + `tool_choice: none` 复用缓存）；
  短会话可省 2–3%。
- `turn_summary` 在非 xAI 后端直接跳过，避免每轮一次必然失败的请求。

## 4. 顺序与验收（2026-11-14 定稿）

1. **第一步（已完成）：** P1 窗口配置——glm/deepseek `400000` / `72` / output 65,536，
   luna `256000` / `85` / output 32,768；只对新会话生效。
2. **第二步：** P2 压缩后基线多档归因（17/26/40/66k），只读诊断，先不改保留量或
   压缩模式。
3. **第三步：** A 组三项——压缩调用入账、`turn_summary` 非 xAI 跳过、title refresh 截断。
4. **第四步：** 内建工具延迟声明——先拉 30 天使用统计，只对零调用子集（`workflow`、
   `image_*`、`reference_to_video`、`send_feedback`、`scheduler_*`、`lsp`）做静态
   隐藏/延迟；发现机制不稳定就先落静态清单。
5. **暂缓：** subagent reasoning 降档与调用合并——效果不稳定，等工具面稳定后再评估。
6. 验收：窗口调整按“甜区占比 ≥25%、无超窗、压缩次数下降”验收，`$/call` 允许 +10% 以内；
   其他省钱项仍按 `$/call` 降 ≥8% 且返工不上升验收；归因需能解释四档基线来源。

## 6. 明确不做

- 不把压缩水位压到 200k 以下：会牺牲 200–300k 的注意力窗口。
- 不用 `400K/80%`（320k 触发）：约 9% 的调用会越过 300k 的甜区上界。
- 不做缓存断崖专项：3 条记录、0.04% 成本，没有空间。
- 不启动完整 code-mode：与本次成本结构无关，另案评估。
